# Аудит RAG по корпоративным документам

## Вывод

Корпоративный RAG — не «чат поверх PDF», а управляемая цепочка происхождения данных: граница корпуса → безопасное извлечение → воспроизводимое разбиение → единая embedding-модель → измеряемый retrieval → grounded generation → цитаты и eval. Главный источник качества — не размер LLM, а правильная область поиска, полнота парсинга и измеряемая релевантность.

Реализация выбирает пространства знаний, PostgreSQL/pgvector, русский full-text search, RRF,
provider-границу для GigaChat/Ollama и постраничный vision-разбор инструкций. Это даёт понятный продукт и
оставляет путь к RBAC, специализированному OCR для низкокачественных сканов и reranker без
переписывания интерфейса.

## Как строится pipeline

1. **Corpus boundary.** Связанные документы получают общий `space_id`; это одновременно пользовательский контекст и обязательный SQL-фильтр.
2. **Ingestion.** Расширение и размер проверяются, файл хешируется, сохраняется, а durable job попадает в PostgreSQL. Повторный hash не создаёт вторую версию.
3. **Extraction.** Форматный extractor сохраняет location: страницу, слайд, лист или таблицу. Скан без текстового слоя честно завершится ошибкой — скрытый «пустой успех» опаснее.
4. **Chunking.** Фрагмент должен быть достаточно мал для embedding и достаточно целостен для ответа. Overlap предотвращает потерю правила на границе.
5. **Indexing.** Один текстовый фрагмент имеет один 1024-мерный вектор выбранной модели и FTS-представление. Модель индекса фиксирована до полного reindex.
6. **Retrieval.** Семантический канал находит перефразирование, лексический — точные термины, номера и фамилии. RRF объединяет ранги, не смешивая несопоставимые cosine и `ts_rank`.
7. **Generation.** В prompt попадают только top-6, filename/location и жёсткая инструкция игнорировать команды внутри контекста. История ограничена шестью сообщениями.
8. **Evidence.** API возвращает ответ, источник, excerpt и score; пользователь проверяет факт, а eval сравнивает ожидаемый источник.

## Актуальные ограничения GigaChat

Проверка выполнена 04.08.2026 по официальной документации:

- целевой REST URL с 17.07.2026 — `https://api.giga.chat`; OAuth access token действует 30 минут, `scope` обязателен ([авторизация](https://developers.sber.ru/docs/ru/gigachat/api/reference/rest/gigachat-api));
- `GigaChat-2-Pro` имеет контекст 128 тыс. токенов и предназначен для сложных инструкций/QA ([выбор модели](https://developers.sber.ru/docs/ru/gigachat/guides/selecting-a-model), [обновления](https://developers.sber.ru/docs/ru/gigachat/models/updates));
- `Embeddings-2`: окно 512 токенов, вектор 1024 ([описание модели](https://developers.sber.ru/docs/ru/gigachat/models/embeddings-2)); `EmbeddingsGigaR`: 4096 токенов и 2560 координат ([описание GigaR](https://developers.sber.ru/docs/ru/gigachat/models/embeddings-giga-r));
- в среднем токен содержит 3–4 символа; точную оценку даёт `/tokens/count`; физлицу доступен один поток, юрлицу по умолчанию десять ([квоты](https://developers.sber.ru/docs/ru/gigachat/limitations)).

Для TLS нужен корневой сертификат НУЦ Минцифры ([официальная инструкция](https://developers.sber.ru/docs/ru/gigachat/certificates)). Сертификат включён в `certs/`, его SHA-256 fingerprint проверен: `D2:6D:2D:02:31:B7:C3:9F:92:CC:73:85:12:BA:54:10:35:19:E4:40:5D:68:B5:BD:70:3E:97:88:CA:8E:CF:31`. Отключать TLS verification для рабочего режима не требуется.

Отсюда выбран chunk 1100 символов: примерно 275–367 токенов по официальной средней оценке, с резервом до окна 512. Шесть retrieval-фрагментов и output limit 1200 оставляют большой запас относительно 128k контекста Pro. Это консервативная оценка, а не гарантия tokenizer; 422 должен считаться наблюдаемой ошибкой.

## Текущий токен-бюджет

На предоставленном скриншоте от 04.08.2026 показаны: 44 167 349 embedding-токенов из пакета 50 млн до 31.03.2027; 284 434 Pro-токена из отдельного пакета 1 млн до 23.10.2026; также подписочный баланс Pro 40 млн до 23.07.2027. Порядок списания между подпиской и пакетами из скриншота не следует, поэтому продукт его не предполагает.

При среднем chunk около 350 токенов текущий остаток embeddings теоретически покрывает порядка 126 тыс. chunks до учёта overlap, запросов и служебной токенизации. Генерация дороже операционно, поэтому ответы ограничены 1200 токенами, история — шестью сообщениями, а CI всегда использует fake provider.

## Разбор альтернатив

| Решение | Плюс | Почему не выбрано сейчас |
| --- | --- | --- |
| Прямые file attachments в chat | минимальный код | контекстное окно, слабая повторяемость, нет единого cross-document retrieval |
| Chroma/FAISS | быстрый прототип | отдельная persistence/backup-модель и слабее транзакционная связь с документами |
| Только vector search | простота | хуже на артикулах, лимитах и точных корпоративных терминах |
| LangChain pipeline | много готовых интеграций | скрытые defaults и сложнее локализовать качество/ошибку |
| EmbeddingsGigaR | больше окно, потенциально выше quality | 2560 dimensions требуют другой pgvector schema и измеримого выигрыша на eval |

## Основные риски

- **Парсинг:** vision обрабатывает обычные скриншоты и выделения, но мелкий/размытый текст может
  быть потерян. Для таких входов нужен измеряемый OCR fallback.
- **Prompt injection:** документ может просить модель игнорировать систему. Защита снижает, но не устраняет риск; нельзя давать модели side-effect tools.
- **Версии:** две противоречивые политики дадут два валидных источника. Нужны effective date и supersedes metadata.
- **Доступ:** без SSO/ACL любой пользователь локального сервиса видит все пространства. Это главный production blocker.
- **Оценка:** «ответ выглядит разумно» не является доказательством. Нужны labelled questions, Recall@K, citation precision и answer faithfulness.
- **Внешняя граница:** передача документа GigaChat должна соответствовать корпоративной политике и классификации данных.

## Рекомендованный следующий уровень

После прохождения текущего eval добавить ACL на `space_id`, antivirus/CDR, OCR fallback для
низкокачественных сканов, даты действия документов и трассировку retrieval. Затем измерить
`Embeddings-2` против GigaR на одном corpus. Только статистически подтверждённый прирост Recall@6
оправдывает миграцию всех векторов.
